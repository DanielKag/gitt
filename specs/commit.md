# gitt commit — create & amend commits from `gitt status`

- **ID prefix:** `CMT`
- **Status:** in progress — TDD (unit + e2e)
- **Command:** part of `gitt status` (no new subcommand); the `c` / `a` keys

## Summary

`gitt status` is the working-tree cockpit; committing is the one write that completes the everyday
loop (see → stage → **commit**). From the file list, `c` opens a centered commit-message editor and
`a` opens it in **amend** mode (prefilled with the current HEAD message). The editor reuses the shared
centered-overlay chrome, theme, and keybinding vocabulary, so it feels like the rest of `gitt`:
`Enter` confirms, `Esc` dismisses (then quits — repeated `Esc` is always the way out), `Ctrl-c` quits.

The message can be typed, or **generated by AI** from the staged diff: in a blank editor `s` (or
`Ctrl-s` anytime) streams a one-line suggestion into the field via the same local-model `Summarizer`
port `gitt log`/`gitt branch` use.

Committing is a **terminal handoff** (like a successful `gitt branch` checkout): on `Enter`, gitt tears
down the TUI, **echoes the `git commit …` command, and runs it in the restored terminal with inherited
stdio** — so a `pre-commit` hook (lefthook, husky, …) streams its progress live, a hook/commit failure
stays on screen with git's own output, and the echoed command line is right there to fix-and-re-run.
gitt then exits with git's status code. It does **not** run the commit on a hidden worker thread.

By design `gitt` owns only the safe, non-history-rewriting everyday writes (stage/unstage/discard/
commit/amend) and deliberately refuses rebase, merge, conflict resolution, and force-push.

## Keybindings / UX

| Key             | Mode   | Action                                                          |
| --------------- | ------ | -------------------------------------------------------------- |
| `c`             | List   | Open the commit editor (normal commit)                         |
| `a`             | List   | Open the commit editor in amend mode (prefill HEAD's message)  |
| printable (incl. `s`) | Commit | Append to the message                                    |
| `Backspace`     | Commit | Delete the last character                                     |
| `Ctrl-s`        | Commit | Suggest an AI message from the staged diff (streamed; regenerates over a draft) |
| `Enter`         | Commit | Commit / amend (no-op on an empty message)                    |
| `Esc`           | Commit | Cancel the editor (back to List)                              |
| `q` / `Ctrl-c`  | any    | Quit                                                          |

_Suggest is `Ctrl-s`, not bare `s`: the editor is a free-text field and many commit subjects start
with "s" ("ship", "start", "support"), so a bare-`s` command would hijack them. `Ctrl-s` is
collision-free (raw mode clears terminal flow control) and reads as "suggest". `c`/`a` are unused
across every other screen._

## Ports & seams

- The commit itself is **not** a `GitRepo` port method — it runs in the restored terminal after the
  TUI exits (`runtime::run` → `run_exit_command`), driven by the pure `domain::commit_command(message,
  amend) -> CommitInvocation { args, display }` (shell-quoted `display` is echoed; `args` are passed to
  `git` literally). The `Screen::exit_command` seam is how a screen defers a foreground command.
- `head_message()` (behind `GitRepo`) — `git log -1 --pretty=%B` (trimmed); the amend prefill (full
  body preserved).
- `staged_diff()` (behind `GitRepo`) — `git diff --no-color --staged -w`; the AI suggestion's input.

## Errors / edge cases

- Nothing staged + non-amend → refused inline (CMT-04), no `git commit` spawned.
- Empty message + `Enter` → no-op, editor stays open (CMT-02).
- Amend with no commit yet (`git log -1` fails) → inline hint, editor stays open, no crash.
- A failed `git commit` (e.g. a rejecting pre-commit hook) is shown by git itself in the restored
  terminal, gitt exits non-zero, and the echoed command line lets the user fix and re-run it.
- Interactive stdin during the commit (e.g. a GPG `pinentry-tty`, an interactive hook) is a known
  edge: gitt's input reader may still be attached to the terminal. The common non-interactive hook
  (lint/test scripts writing to stdout/stderr) works cleanly.
- AI suggestion failure (`ollama` down) → inline hint in the editor; the field stays editable.
- Message body: `Enter` commits, so newlines can't be *typed* (subject-only authoring); an amend
  prefill preserves any existing multi-line body verbatim so amending never drops it.

## Out of scope (for this POC)

- Multi-line body authoring in the editor (subject-only; amend preserves an existing body).
- Partial/hunk staging, sign-off/GPG, commit templates, hooks management.
- push / pull / fetch and any history-rewriting op (rebase/merge/conflict resolution) — by design.
